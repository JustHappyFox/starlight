# wm_watchdog — сторож для асиков Whatsminer

Каждую минуту опрашивает асики по их родному API. Если асик перестал хешировать
(например, отвалился по питанию/напряжению с ошибкой 2xx), скрипт **сам перезагружает его
через API** (это та же кнопка «Reboot», что и в веб-морде), пишет в **Telegram** и
ведёт журнал инцидентов, по которому видно, какой асик, когда и с какими ошибками падает.

* Один файл `wm_watchdog.py`, **без зависимостей**: нужен только Python 3.8+
  (Windows, Linux, Raspberry Pi, мини-ПК).
* API v2 (порт 4028: M2x/M3x/M5x на большинстве прошивок) и API v3 (порт 4433: M6x и
  прошивки новее ~2024) — версия определяется сама.
* Защита от ребут-циклов: не чаще 3 действий в час на асик. Если не помогает, приходит
  «⛔ нужен осмотр».
* Режим `--dry-run`: только смотреть и уведомлять, ничего не трогать.

## 1. Разрешить управление асиками по API (один раз)

По умолчанию асик отдаёт только чтение. Чтобы скрипт мог перезагружать асики, нужна
**WhatsMinerTool** (официальная утилита MicroBT для Windows):

1. **Смени пароль admin.** WhatsMinerTool → выделить асики → смена пароля (Change
   Password). С заводским паролем `admin` запись по API на многих прошивках **не
   работает**, даже если API включён. Пароль может быть любым, но сменить его надо.
2. **Включи API.** Remote Ctrl → **API Switch** (Miner API Switch) → Enable.
   Нужна прошивка от 2020-08-01 или новее.
3. Для API v3 (M6x / новые прошивки) учётка `super`, пароль по умолчанию `super`. Если
   ты его менял, укажи новый в `password_v3`.

## 2. Установка

```bash
# Python 3.8+ (на Windows: python.org, при установке поставь галку «Add to PATH»)
cd whatsminer-watchdog
cp config.example.ini config.ini        # на Windows: copy config.example.ini config.ini
python3 wm_watchdog.py scan 192.168.1.0/24   # найти асики, выведет готовые строки для конфига
```

На Windows вместо `python3` пиши `python` (или `py`).

В `config.ini` впиши асики в секцию `[miners]` и пароль admin из шага 1. Затем:

```bash
python3 wm_watchdog.py status       # таблица: хешрейт, норма, аптайм, ватты, вход БП (В), ошибки, платы
python3 wm_watchdog.py check-auth   # проверка, что запись по API пускает (LED → авто)
python3 wm_watchdog.py run --dry-run   # первые сутки: только смотрит и пишет, не ребутит
python3 wm_watchdog.py run          # боевой режим
```

Если `check-auth` пишет «Запись по API выключена» или «неверный пароль», вернись к шагу 1.

### Telegram

1. Создай бота у [@BotFather](https://t.me/BotFather) и скопируй токен.
2. Напиши своему боту что угодно.
3. Открой `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найди `"chat":{"id": ...}`.
4. Заполни `token` и `chat_id` в `[telegram]`, затем выполни
   `python3 wm_watchdog.py telegram-test`.

Какие сообщения приходят:
* 🔄 асик упал (причина, коды ошибок с расшифровкой) и отправлена перезагрузка;
* ✅ снова хеширует (сколько длился простой);
* 📵 асик не отвечает вообще (по API его уже не перезагрузить, см. `on_unreachable`);
* ⛔ 3 перезагрузки за час не помогли, нужен осмотр;
* ❌ команда не прошла (например, API не включён);
* 📊 ежедневная сводка (`daily_report_hour`).

Если `api.telegram.org` у тебя режется, есть два варианта: задать `api_url` (зеркало или
прокси Bot API) или переменную окружения `HTTPS_PROXY` (её понимает встроенный HTTP-клиент
Python).

### Автозапуск

**Linux / Raspberry Pi (systemd).** Поправь пути в `wm-watchdog.service`, затем:

```bash
sudo cp wm-watchdog.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now wm-watchdog
journalctl -u wm-watchdog -f        # смотреть лог
```

**Windows.** Файл `start_windows.bat` запускает сторожа и перезапускает его, если он
упадёт. Чтобы стартовал вместе с Windows: Win+R → `shell:startup` → положи туда ярлык на
`start_windows.bat`. Есть вариант надёжнее: Планировщик заданий → «При запуске
компьютера» → запускать `start_windows.bat` от имени пользователя, «выполнять для всех
пользователей». Компьютер, где крутится сторож, не должен засыпать.

## 3. Как сторож решает, что асик упал

Каждые `interval` секунд (по умолчанию 60) он читает `summary`, `devs`, `get_error_code`
и `get_psu` (входное напряжение БП). Асик считается упавшим, если:

* хешрейт 0;
* одна из плат перестала хешировать (`check_dead_boards`);
* хешрейт ниже `min_hashrate_pct`% от нормы. Норма — это `expected_ths` из конфига, а
  если его нет — заводской хешрейт, который отдаёт сам асик;
* асик стоит в «прогреве» дольше `grace_period` и не хеширует, то есть btminer
  зациклился в перезапусках.

Когда это держится `bad_checks` проверок подряд (по умолчанию 3 минуты), выполняется
действие из `actions`. По умолчанию это `reboot`; можно задать цепочку
`restart, reboot`. После действия сторож ждёт `action_cooldown`, а первые `grace_period`
секунд после старта майнера асик не трогает: он греется и подбирает частоты.

Коды ошибок **сами по себе ребут не вызывают**: старые ошибки висят в списке и после
восстановления. Решает только хешрейт. Ошибки нужны для уведомлений и статистики.

Если асик не отвечает совсем (завис контроллер, пропало питание или сеть), по API его не
перезагрузить. Придёт 📵. Есть вариант лучше: настроить `on_unreachable`, например
передёрнуть умную розетку или реле (Shelly/Sonoff/управляемый PDU). Пример есть в
`config.example.ini`.

## 4. Все команды

| Команда | Что делает |
|---|---|
| `run [--dry-run]` | следить и чинить (основной режим) |
| `status` | таблица по всем асикам |
| `check-auth` | проверить доступ на запись по API |
| `reboot <имя\|IP\|all>` | перезагрузить вручную |
| `restart <имя\|IP\|all>` | перезапустить только btminer |
| `power-limit <имя\|IP\|all> <Вт>` | ограничить мощность (асик перезапустит майнер) |
| `power-mode <имя\|IP\|all> low\|normal\|high` | режим мощности (API v2) |
| `report [--days 7]` | статистика: кто сколько падал, частые коды, падения по часам |
| `scan 192.168.1.0/24` | найти асики в сети |
| `telegram-test` | проверить Telegram |

## 5. Почему они вообще отваливаются по напряжению

Сторож убирает ручные перезагрузки, но причину не лечит. 5–6 падений в день у одних и тех
же 2–3 асиков — это почти всегда **БП, проводка или напряжение в сети**. Через
пару дней работы запусти `python3 wm_watchdog.py report`: там видны коды ошибок и часы, в
которые асики падают.

Как читать отчёт:

* **Падают одни и те же асики, а соседи на той же линии живут.** Скорее всего, виноват
  **блок питания** этих асиков. Проверка: поменяй БП местами с исправным асиком. Если
  ошибки переехали вместе с БП, дело в нём.
* **Падают в одно время, часто ночью или когда включается что-то мощное.** Скорее всего,
  **сеть**: напряжение проседает или скачет. Входное напряжение БП видно в `status`
  (колонка «вход В»), пишется в журнал и в уведомление о падении. В `report` для каждого
  асика есть строка «вход БП при падениях: … В, после восстановления: … В». Если при
  падениях оно заметно ниже, проблема в сети.

Что значат частые коды (по официальной таблице MicroBT):

| Коды | Что это | Что делать |
|---|---|---|
| 206, 250–251, 271 | низкое входное напряжение | проверить сеть под нагрузкой, сечение и скрутки, автоматы; стабилизатор |
| 248–249, 270 | высокое входное напряжение | то же, особенно ночью |
| **218** | ниже 230 В в режиме **High** | **выключить High-режим** (`power-mode <асик> normal`) или поднять напряжение |
| 202, 209, 212, 215 | выходное напряжение БП «уплыло» | обновить прошивку; если повторяется — БП |
| 208, 211, 213, 216, 217, 219, 241, 502X | БП нестабилен или деградировал | замена БП |
| 236–238, 268 | перегрузка по выходному току | **подтянуть винты медных шин** между БП и платами |
| 203–204, 233–235, 243–245, 255–256, 275 | перегрев БП | температура в помещении, пыль, обдув |
| 253–254, 274 | вентилятор БП | почистить или заменить вентилятор (или БП) |
| 263–264 | нет связи с БП | подтянуть винты/шлейф платы управления |
| 258–259 | перекос фаз | разбросать нагрузку по фазам |

Что можно сделать на стоковой прошивке без перепрошивки:
* снизить нагрузку на БП: `power-mode <асик> low` или `power-limit <асик> <Вт>` (например,
  на 10–15% ниже текущего потребления). Слабый БП или просевшая сеть часто перестают
  выбивать, а хешрейта теряется меньше, чем на простоях. Слишком низкий лимит может
  вогнать асик в бесконечные перезапуски, так что снижай постепенно;
* не держать асики в режиме High при напряжении ниже 230 В (ошибка 218).

## 6. Про кастомные прошивки «с настройкой каждого чипа»

Состояние на ноябрь 2026. Часть данных о сторонних прошивках взята из поисковых выдержек:
сайты производителей напрямую не открылись. Перед прошивкой проверь на их сайтах.

* **Поканальной регулировки напряжения на Whatsminer нет физически.** Напряжение на платы
  даёт БП, и оно общее для всех плат. Чипы внутри платы стоят последовательными «доменами»
  и делят это напряжение. «Тюнинг каждого чипа» в любых прошивках на Whatsminer — это
  **частота** каждого чипа плюс одно общее напряжение БП.
* **BiXBiT** поддерживает Whatsminer M2x/M3x/M5x/M6x. Есть автотюн частот по чипам и
  функция «отключать слот при ошибках» со счётчиком восстановительных ребутов.
  Комиссия ~2.8% (на M2x ~2%). Установка зависит от платы управления: на части плат со
  свежей стоковой прошивкой сначала нужен даунгрейд, на H616 — прошивка через SD-карту.
* **LuxOS** (Luxor) поддерживает Whatsminer с апреля 2026, но только часть моделей M50/M60
  (ревизии VH/VK/VL). Установка через партнёров и заявку. Про M30S данных нет.
* **VNish, Braiins OS+, Hiveon** прошивок для Whatsminer не делают (только для Antminer).
  Сайты, где пишут «VNish на M30S», устарели или ошибаются.
* Риски: потеря гарантии MicroBT. На свежих стоковых прошивках откат запрещён. Неверный
  образ для твоей платы управления может её окирпичить. Перед прошивкой посмотри тип платы
  (H3/H6/H616 и т. п.) в WhatsMinerTool.

**Вывод:** если асики падают из-за БП или сети, кастомная прошивка это не вылечит. Она
может только снизить нагрузку и подобрать частоты, а снизить нагрузку можно и на стоке
(`power-limit`/`low`). Сначала сторож и отчёт, чтобы понять, где виноват БП, а где сеть.
Прошивку имеет смысл рассматривать уже ради эффективности (J/TH).
